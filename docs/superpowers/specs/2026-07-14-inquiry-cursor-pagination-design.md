# Inquiry Cursor Pagination Design

## Goal

새 문의가 등록된 뒤에도 문의 목록의 다음 페이지에서 중복과 누락이 생기지 않도록 커서 기반 페이지네이션으로 전환한다.

## Constraints

- Supabase 스키마, RLS, 기존 문의·금융 데이터는 변경하지 않는다.
- 기존 `inquiries` 테이블만 읽는다.
- 사용자 문구는 한국어로 유지한다.
- 운영 Supabase 원격 적용, 마이그레이션, 배포를 수행하지 않는다.

## Data flow

`getInquiries`는 선택적 커서와 페이지 크기를 받고, `created_at DESC, id DESC` 순서로 한 페이지보다 한 건 더 읽는다. 반환값은 표시 항목, 다음 페이지 존재 여부, 마지막 표시 항목에서 만든 다음 커서다.

첫 요청에는 커서가 없다. 다음 요청은 마지막 표시 항목의 `{ createdAt, id }`를 전달한다. 서버 쿼리는 `created_at`이 더 과거인 항목 또는 생성 시각은 같고 `id`가 더 작은 항목만 가져온다. 따라서 새 문의가 목록 맨 앞에 추가되어도 이전 페이지의 경계는 바뀌지 않는다.

## UI state

문의 페이지는 `nextCursor`를 상태로 보관한다. 초기 로드가 이 값을 설정하고, 더 보기는 이 값을 사용한다. 새 문의를 앞에 추가해도 `nextCursor`는 유지한다. 중복 방지 병합은 방어 장치로 남긴다.

## Error handling and testing

기존 읽기 오류는 그대로 사용자 알림으로 전달한다. 단위 테스트는 첫 페이지의 look-ahead, 복합 커서 필터, 동일 `created_at`에서 `id` tie-break, 새 항목 삽입 뒤 다음 커서 사용을 검증한다. UI는 더 보기 버튼이 로딩 중 비활성화되는 기존 동작을 유지한다.

## Self-review

- 커서는 `created_at`만으로 만들지 않고 `id`를 포함하므로 동시 생성 순서가 안정적이다.
- 테이블·인덱스·정책 변경은 포함하지 않는다.
- offset 방식과 호환되는 공개 API는 없으므로 내부 API 시그니처 변경 범위는 문의 페이지와 테스트로 한정된다.
