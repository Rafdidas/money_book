# 사용자 카테고리 관리와 자주 쓰기 설계

## 목적

기본 카테고리는 앱의 고정 선택지로 유지하면서, 사용자가 지출·수입·저축·투자
유형별로 자신만의 카테고리를 추가·이름 수정·삭제할 수 있게 한다. 사용자
카테고리 중 일부는 `자주 쓰는 카테고리`로 지정해 거래 입력 화면에서 바로
선택할 수 있게 한다.

기존 거래는 카테고리 이름을 문자열로 보관한다. 사용자 카테고리를 수정하거나
삭제해도 이미 저장된 거래의 카테고리 값은 변경하지 않는다.

## 기존 구조와 선택한 접근

현재 `user_custom_categories` 테이블은 사용자, 거래 유형, 정규화된 이름,
최근 사용 시각을 저장하며 사용자별 RLS와 이름 중복 방지 제약을 갖고 있다.
거래를 직접입력 카테고리로 저장하면 이 테이블에 upsert하고, 거래 입력 폼에는
유형별 최근 5개를 칩으로 보여준다. 데모 모드는 같은 형태를 버전형
localStorage에 저장한다.

새 테이블이나 별도 즐겨찾기 테이블을 만들지 않고 기존 테이블을 정식 사용자
카테고리 저장소로 확장한다. 이 방식은 기존 사용자 데이터, RLS, 이름 정규화와
직접입력 저장 흐름을 그대로 활용하면서 기능 간 규칙을 한곳에 유지한다.

## 범위

- 사용자 카테고리 전체 조회
- 유형별 사용자 카테고리 추가, 이름 수정, 삭제
- 사용자 카테고리의 `자주 쓰기` 설정과 해제
- 유형별 자주 쓰는 카테고리 최대 5개 제한
- 거래 입력 폼의 빠른 선택 칩과 카테고리 관리 모달
- 마이페이지의 카테고리 관리 카드
- 로그인 사용자와 데모 사용자 모두 동일한 기능 제공

다음은 범위 밖이다.

- 기본 카테고리 추가, 수정, 삭제
- 기본 카테고리의 자주 쓰기 지정
- 사용자 카테고리 수동 정렬
- 카테고리 수정·삭제 시 과거 거래 일괄 변경
- 카드 관리와 카드 실적 추적

## 데이터 모델

`public.user_custom_categories`에 다음 열을 추가한다.

- `is_favorite boolean not null default false`

기존 행은 모두 일반 사용자 카테고리로 유지하고 즐겨찾기는 해제 상태로
시작한다. 기존 `unique (user_id, entry_type, normalized_name)` 제약과 RLS를
유지한다.

동일 사용자와 유형에서 `is_favorite = true`인 행은 최대 5개만 허용한다.
화면에서 먼저 여섯 번째 지정을 막고, 데이터베이스에서도 트랜잭션 단위로
검증해 동시에 요청해도 6개가 저장되지 않게 한다. 제한 초과 오류는
애플리케이션에서 사용자용 한국어 안내로 변환한다.
데이터베이스 trigger는 사용자와 유형 조합에 대한 transaction-level advisory
lock을 획득한 뒤 현재 즐겨찾기 수를 검사해 경쟁 요청에서도 제한을 보장한다.


## 카테고리 규칙

- 유형은 `expense`, `income`, `savings`, `investment` 네 가지다.
- 이름은 앞뒤 공백을 제거하고, 같은 유형에서 영문 대소문자만 다른 이름은
  중복으로 취급한다.
- 서로 다른 유형에서는 같은 표시 이름을 각각 사용할 수 있다.
- 같은 유형의 기본 카테고리와 표시 이름이 같은 사용자 카테고리는 추가하거나
  변경할 수 없다.
- 직접입력으로 거래 저장에 성공하면 해당 이름을 사용자 카테고리에 upsert한다.
  새로 생긴 카테고리는 즐겨찾기로 자동 지정하지 않는다.
- 사용자 카테고리 이름 수정은 카테고리 행만 바꾼다. 과거 거래 문자열은
  변경하지 않는다.
- 사용자 카테고리 삭제도 카테고리 행만 지운다. 과거 거래는 남는다.
- 삭제한 카테고리가 현재 거래 폼에 선택되어 있으면 해당 폼의 카테고리 선택만
  현재 유형의 안전한 기본값으로 초기화한다.

## API와 상태 구조

기존 `src/lib/api/customCategories.ts`를 정식 카테고리 API로 확장한다.

- 사용자 카테고리 전체 조회
- 이름과 유형 기준 upsert
- ID 기준 이름 수정
- ID 기준 삭제
- ID 기준 즐겨찾기 설정·해제

전체 목록은 유형 안에서 즐겨찾기를 먼저, 같은 상태에서는 `last_used_at`이
최근인 순서로 정렬한다. 직접입력 거래 저장으로 upsert할 때만 최근 사용 시각을
명시적으로 갱신하고, 이름 수정이나 즐겨찾기 변경은 이를 바꾸지 않는다. 이를
위해 현재 모든 update에서 최근 사용 시각을 갱신하는 database trigger도 함께
조정한다.

모든 변경 요청은 인증 사용자의 ID 조건을 포함하고 기존 RLS를 통과해야 한다.
이름 정규화, 기본 카테고리 충돌, 유형별 즐겨찾기 개수처럼 렌더링과 독립적인
규칙은 순수 함수로 분리한다.

로그인/데모 데이터 원본을 선택하고 로드·변경 상태를 관리하는 공통 훅을 둔다.
홈 화면은 이 훅의 카테고리 상태를 빠른 선택 칩, select 선택지, 관리 모달에
전달한다. 마이페이지는 같은 훅과 관리 컴포넌트를 사용한다. 두 화면은 동시에
마운트되지 않으므로 별도 전역 저장소는 도입하지 않으며, 화면 진입 시 영속
저장소에서 최신 값을 다시 읽는다.

데모 저장소는 새 필드를 포함하는 버전으로 올린다. 기존 버전의 유효한 행은
`isFavorite: false`로 마이그레이션해 사용자가 만든 이름을 잃지 않는다.

## 공통 관리 컴포넌트

`CategoryManager`는 데이터 저장을 직접 소유하지 않고 다음 값과 동작을 받는
재사용 가능한 컴포넌트로 둔다.

- 카테고리 목록과 선택된 유형
- 로드·추가·수정·삭제·즐겨찾기 변경 상태
- 유형 변경과 CRUD 콜백
- 선택적 `카테고리 사용` 콜백

거래 입력 화면에서는 모달 안에 렌더링하고 `카테고리 사용` 콜백을 제공한다.
마이페이지에서는 넓은 카드 안에 렌더링하고 선택 콜백은 생략한다. 이렇게 해서
두 위치의 입력 검증과 행 동작이 달라지는 것을 막는다.

## 거래 입력 사용자 경험

- 카테고리 영역에 현재 거래 유형의 자주 쓰는 사용자 카테고리를 최대 5개
  칩으로 표시한다. 하나도 없으면 칩 영역을 렌더링하지 않는다.
- 칩을 누르면 해당 사용자 카테고리를 즉시 선택한다.
- 기존 select는 `기본 카테고리`, `내 카테고리`를 구분해 보여주고
  `직접 입력` 선택지는 유지한다.
- `카테고리 관리` 버튼은 관리 모달을 연다.
- 모달은 지출·수입·저축·투자 탭, 새 이름 입력, 사용자 카테고리 행 목록을
  제공한다.
- 각 행에는 자주 쓰기 별표, 이름 수정, 삭제, `이 카테고리 사용` 동작이 있다.
- 모달에서 성공한 변경은 모달을 닫기 전에도 거래 폼의 칩과 선택 목록에 즉시
  반영한다.

## 마이페이지 사용자 경험

마이페이지에 `카테고리 관리` 카드를 추가하고 같은 `CategoryManager`를 넓은
형태로 렌더링한다. 로그인 사용자는 Supabase 데이터를, 데모 사용자는 데모
localStorage 데이터를 관리한다. 기존 데모 계정 안내는 유지하되 카테고리 관리
카드는 데모에서도 사용할 수 있게 한다.

## 오류와 경계 조건

- 초기 조회 실패는 거래 화면이나 마이페이지 전체를 막지 않는다. 카테고리 관리
  영역에 오류와 `다시 시도` 동작을 제공한다.
- 변경은 영속 저장 성공 후 화면 상태에 반영한다. 실패하면 기존 목록과 현재
  거래 입력값을 유지한다.
- 유형별 즐겨찾기가 5개면 나머지 해제 상태 별표를 비활성화하고 이유를
  표시한다. 기존 즐겨찾기 해제는 계속 가능하다.
- 중복 이름, 빈 이름, 기본 카테고리 이름 충돌은 입력란 가까이에 안내한다.
- 삭제 전 카테고리 이름과 `기존 거래 내역은 변경되지 않습니다` 문구를 포함한
  확인을 받는다.
- 변경 중인 행만 잠가 중복 요청을 막고 다른 행의 탐색은 유지한다.
- 서버에서 즐겨찾기 제한 오류가 발생하면 목록을 다시 불러와 실제 서버 상태와
  맞춘다.

## 접근성과 반응형

- 모달은 의미 있는 제목, 초점 이동, ESC 닫기, 배경 스크롤 차단을 지원한다.
- 별표, 이름 수정, 삭제, 사용 버튼의 접근 가능한 이름에 카테고리 이름을
  포함한다.
- 상태와 오류 문구는 보조 기술이 인식할 수 있게 연결한다.
- 모바일에서도 모든 핵심 조작 영역을 최소 44px로 유지한다.
- 긴 이름은 관리 목록에서 내용을 확인할 수 있어야 하며, 빠른 선택 칩에서는
  레이아웃을 밀어내지 않게 말줄임 처리한다.

## 검증

- 순수 함수 테스트: 유형별 분리, 정렬, 이름 정규화, 기본 이름 충돌,
  즐겨찾기 5개 제한, 추가·수정·삭제 상태 변환
- API 테스트: 전체 조회, upsert, 이름 수정, 삭제, 즐겨찾기 설정·해제,
  인증 사용자 범위, 오류 전파
- 데모 저장소 테스트: 이전 버전 복원, 새 버전 재저장, 즐겨찾기 유지
- 컴포넌트 테스트: 유형 탭, 추가, 인라인 수정, 삭제 확인, 별표 제한,
  모달의 카테고리 선택
- 홈 연동 테스트: 즐겨찾기 칩 선택, 기본/사용자 select 구분, 관리 결과 즉시
  반영, 현재 선택 삭제 시 초기화
- 마이페이지 테스트: 로그인과 데모 양쪽에서 관리 카드 노출
- 수동 시각 검증: 데스크톱과 모바일 너비에서 모달, 마이페이지 카드, 긴 이름,
  빈 상태, 오류 상태 확인
- 전체 검증: `npm test`, `npm run lint`, `npm run build`

## 배포 순서

`is_favorite` 열과 데이터베이스 측 5개 제한을 추가하는 Supabase 마이그레이션을
애플리케이션보다 먼저 배포한다. 기존 행은 기본값으로 호환되므로 별도 데이터
백필이나 과거 거래 변경은 하지 않는다.
