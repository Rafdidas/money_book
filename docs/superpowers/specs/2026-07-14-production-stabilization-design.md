# Money Book 운영 안정화 설계

## 목적

운영 중인 Money Book의 기존 사용자 데이터와 주요 사용자 흐름을 보존하면서 다음
두 우선순위를 실제 운영 환경까지 안전하게 반영한다.

1. 즉시 안정화: Next.js 보안 업데이트, 자동화 테스트, 다중 데이터 변경의 원자성
2. 구조 및 운영 안정성: 대형 클라이언트 화면 분리, 명시적 데이터 분류, 오류 복구,
   API 오류 정리, 보안 헤더, 공개 API 보호, 문의 페이지네이션

## 절대 제약

- 운영 데이터의 손실, 중복, 금액 변경, 사용자 간 노출을 허용하지 않는다.
- 운영 DB 변경과 앱 배포는 백업과 스테이징 검증을 통과한 뒤 수행한다.
- 기존 테이블과 컬럼은 새 경로의 안정화가 끝나기 전에 삭제하거나 의미를 바꾸지 않는다.
- 각 릴리스는 이전 앱 버전으로 되돌릴 수 있어야 한다.
- 운영 Supabase 작업과 배포는 실행 직전에 대상 프로젝트와 백업 상태를 확인한다.
- 사용자에게 보이는 문구는 한국어를 유지한다.
- Next.js 코드를 변경하기 전 `node_modules/next/dist/docs/`의 관련 문서를 확인한다.

## 범위

### 포함

- Next.js `16.2.4`에서 검증된 패치 버전 `16.2.10`으로 업데이트
- `npm audit`에서 확인된 직접·전이 의존성 취약점의 범위별 처리
- Vitest 기반 단위·통합 테스트와 Playwright 기반 핵심 E2E 테스트
- 전역 및 앱 오류 복구 화면과 재시도 경로
- 종목 API의 공개 오류 메시지, 서버 로그, timeout, 입력 및 요청량 보호
- CSP를 포함한 보안 헤더 도입
- 문의 목록의 서버 페이지네이션
- 대시보드, 투자, 분석 화면의 동작 보존형 책임 분리
- 레거시 문자열 추론을 대체할 명시적 entry source/type 데이터 모델
- 적금·고정지출의 복수 행 변경을 위한 Supabase 트랜잭션 RPC
- 스테이징 검증, 운영 마이그레이션, 운영 배포, 스모크 테스트, 롤백

### 제외

- 새로운 재무 기능 또는 화면 디자인 변경
- 기존 금액 계산 규칙의 제품적 변경
- 기존 행이나 컬럼의 즉시 삭제
- 사용자 동의 없는 데이터 의미 재분류
- 테스트 및 검증 없이 실행하는 `npm audit fix`

## 접근 방식

### 선택한 방식: 단계적 무중단 전환

안정화 작업을 서로 독립적인 릴리스로 나눈다. 보안 업데이트, 테스트 기반, 오류 및
API 보완, 구조 분리, DB 확장, 호환 앱 전환을 각각 검증하고 배포한다. 한 단계에서
문제가 발생하면 이후 단계를 진행하지 않고 해당 앱 릴리스만 되돌린다.

일괄 변경은 원인 분리와 롤백이 어렵고, 최소 변경은 이미 확인된 데이터 정합성과
유지보수 위험을 남기므로 채택하지 않는다.

## 릴리스 구조

### 릴리스 A: 의존성 보안 업데이트

- Next.js를 `16.2.10`으로 명시적으로 업데이트한다.
- Next.js 16의 관련 업그레이드 및 Proxy 문서를 먼저 확인한다.
- lockfile 변경을 검토해 의도하지 않은 주요 버전 변경을 차단한다.
- lint, build, 인증 Proxy, 로그인, 로그아웃, 데모, `/app` 접근 제어, 종목 API를 검증한다.
- 이 릴리스는 DB를 변경하지 않는다.

### 릴리스 B: 회귀 테스트 기반

- Vitest와 React Testing Library로 계산 및 화면 경계 테스트를 추가한다.
- Playwright로 실제 사용자가 수행하는 핵심 흐름을 검증한다.
- 테스트는 현재 동작을 먼저 고정하며 제품 동작을 동시에 변경하지 않는다.
- 필수 회귀 대상은 다음과 같다.
  - 월 시작·말일과 연도 변경의 날짜 범위
  - 수입·지출·저축·투자 합계와 전월 비교
  - 레거시 및 신규 적금·고정지출 매핑
  - 종목 검색 정규화와 점수 순서
  - 로그인 사용자와 데모 데이터의 완전 분리
  - 수입·지출 CRUD와 월 이동
  - RLS에 의한 사용자별 데이터 격리

### 릴리스 C: 오류·보안·운영 보완

- `error.tsx`와 `global-error.tsx`에 재시도 가능한 한국어 오류 화면을 제공한다.
- API 응답에는 내부 공급자 오류나 SQL 오류를 직접 노출하지 않는다.
- 서버 로그에는 요청 ID, 라우트, 실패 단계와 원본 오류를 남기되 개인정보와 키를 기록하지 않는다.
- 외부 주식 데이터 요청에 timeout을 적용하고, 캐시된 데이터가 있으면 일시적 외부 장애 중에도 제한적으로 재사용한다.
- 공개 종목 검색에는 정규화된 쿼리 길이 제한과 요청량 제한을 둔다.
- CSP, HSTS, Referrer-Policy, Permissions-Policy를 단계적으로 적용한다. CSP는 먼저
  Report-Only 또는 로컬 위반 확인을 거쳐 Analytics, Speed Insights, 폰트 리소스를
  명시적으로 허용한 뒤 강제한다.
- 문의 목록은 정렬 기준이 고정된 cursor 페이지네이션을 사용한다.

### 릴리스 D: 동작 보존형 화면 분리

- 대시보드의 인증·조회·CRUD·반복 일정 상태를 전용 hook과 service 경계로 분리한다.
- 투자 화면의 localStorage 캐시, Supabase 저장, 종가 조회, 폼 상태, 파생 계산을 분리한다.
- 분석 화면의 데이터 변환과 표현 컴포넌트를 분리한다.
- 각 추출 단계는 기존 테스트와 데스크톱·모바일 시각 검증을 통과해야 한다.
- 한 릴리스에서 화면 하나만 분리해 회귀 범위를 제한한다.

### 릴리스 E: 추가형 DB 확장

운영 적용 전 동일 스키마의 스테이징 환경에서 아래 변경을 검증한다.

- 기존 데이터를 건드리지 않는 nullable 분류 컬럼 또는 별도 메타데이터 구조 추가
- 기존 API와 RLS를 유지한 채 새 컬럼의 접근 정책 및 인덱스 추가
- 적금·고정지출 복수 행 변경을 하나의 트랜잭션으로 수행하는 RPC 추가
- RPC는 `auth.uid()`를 기준으로 소유권을 확인하고 `security definer` 사용 시 고정된
  `search_path`와 최소 실행 권한을 적용
- 동일 요청 재시도 시 결과가 중복되지 않는 입력과 제약조건 사용

이 단계가 운영에 적용돼도 기존 앱은 기존 컬럼만 사용하므로 동작이 바뀌지 않는다.
DB 객체 추가는 롤백 시 즉시 제거하지 않아도 기존 앱에 영향을 주지 않게 설계한다.

### 릴리스 F: 호환 앱과 검증 가능한 백필

- 새 앱은 명시적 분류가 있으면 이를 우선 사용하고, 없으면 기존 문자열 추론으로 fallback한다.
- 신규 및 수정 데이터에는 기존 형식과 명시적 분류를 함께 기록한다.
- 기존 데이터 백필은 작은 배치로 실행하며 원본 금액, 날짜, 메모, 카테고리를 변경하지 않는다.
- 자동 확정 가능한 행만 백필하고 모호한 행은 레거시 fallback 상태로 남긴다.
- 배치마다 사용자별 행 수, 금액 합계, 월별 합계, 분류별 합계를 전후 비교한다.
- 불일치가 한 건이라도 있으면 배치를 중단하고 앱은 기존 추론을 계속 사용한다.

### 릴리스 G: 레거시 정리

최소 한 번의 운영 관찰 기간 동안 오류율과 합계 검증이 안정적일 때만 별도 설계와
승인을 거쳐 진행한다. 이번 구현 범위에서는 기존 컬럼, 메모 마커, fallback 로직을
삭제하지 않는다.

## 데이터 보호 절차

### 운영 적용 전

1. Supabase 대상 프로젝트 ID와 배포 대상 도메인을 명시적으로 확인한다.
2. 최근 백업 또는 PITR 복구 가능 시점을 확인한다.
3. 스키마와 영향 테이블의 행 수 및 사용자별·월별 금액 합계 스냅샷을 저장한다.
4. 스테이징에서 마이그레이션과 롤백 절차를 반복한다.
5. 장시간 lock을 유발할 수 있는 DDL과 전체 테이블 단일 트랜잭션 백필을 금지한다.

### 운영 적용 중

1. 추가형 DDL만 먼저 적용한다.
2. 마이그레이션 직후 RLS, 함수 권한, 인덱스와 기존 앱 CRUD를 확인한다.
3. 호환 앱을 배포한다.
4. 백필은 크기가 제한된 배치로 실행한다.
5. 각 단계의 검증 결과를 `HANDOFF.md`에 기록한다.

### 운영 적용 후

- 로그인, 데모, 수입·지출 CRUD, 적금, 고정지출, 분석, 투자, 문의를 스모크 테스트한다.
- 배포 전후 사용자별 행 수와 금액 합계를 비교한다.
- API 4xx/5xx, 외부 종목 API 실패율, 클라이언트 오류를 확인한다.
- 이상이 있으면 앱을 이전 버전으로 되돌리고 새 DB 객체는 비활성 상태로 남긴다.
  기존 데이터 값은 변경하지 않으므로 앱 롤백만으로 기존 경로를 복구할 수 있다.

## 오류 처리 원칙

- 사용자는 수행한 작업이 저장됐는지 명확히 알 수 있어야 한다.
- 다중 행 변경은 모두 성공하거나 모두 실패해야 한다.
- 외부 API 일부 실패는 성공 항목과 실패 항목을 구분해 표시한다.
- 재시도는 데이터 중복을 만들지 않아야 한다.
- 운영 로그에는 비밀번호, 인증 토큰, 전체 문의 내용, 전체 메모를 남기지 않는다.

## 테스트 및 검증 게이트

모든 앱 릴리스는 다음 조건을 충족해야 한다.

- `npm run lint` 통과
- 단위·통합 테스트 통과
- `npm run build` 통과
- Playwright 핵심 흐름 통과
- 1280px 데스크톱과 390px 모바일에서 수동 또는 자동 시각 검증
- `git diff --check` 통과
- 해당 릴리스가 DB를 변경한다면 스테이징 전후 데이터 합계 검증 통과

운영 배포 성공 조건은 다음과 같다.

- 기존 사용자별 행 수와 금액 합계 불일치 0건
- RLS 교차 사용자 접근 테스트 실패 0건
- 핵심 CRUD와 인증 스모크 테스트 실패 0건
- high 등급 의존성 취약점 0건 또는 영향 분석과 예외 승인 기록

## 구현 완료 기준

- 1순위와 2순위 항목이 독립적인 릴리스 단위로 구현·검증·운영 반영된다.
- 기존 데이터의 금액, 날짜, 사용자 소유권이 보존된다.
- 기존 데이터는 새 분류가 없어도 계속 정상 표시된다.
- 다중 행 변경은 DB 트랜잭션으로 원자적으로 처리된다.
- 주요 계산, 인증, CRUD, RLS, 데모 흐름이 자동화 테스트로 보호된다.
- 운영 장애 시 문서화된 절차로 이전 앱 버전으로 복구할 수 있다.
